# Rules

Global rules for the KMax launcher and for every project it hosts (each folder next to this one under `Assets/Games/`, for example `KMaxPCBAssembly` and
`kmax-human-anatomy`, and any project added later).

## How these rules are used

- **Before** changing anything in any repository under `Assets/Games/`, read this file.
- **After** the change, check every rule in "Global Rules" below against what was changed. A change is not done until each rule that applies is satisfied.
- Report the result in the hand-off: which rules were checked, and for any rule that is not satisfied, why and what is left to do. Do not skip a rule silently.
- A rule applies to the launcher and to all projects, new and existing, unless it says otherwise.
- These rules sit with the coding rules in `Assets/Games/AGENTS.md`; if the two ever conflict, stop and ask the owner.
- **When working on UI/UX, animations or visuals, follow `docs/Design.md`** (colours, spacing, typography, button feel, motion, sound and the rest). It is the detailed design rule set; R-3 and R-5 are checked against it.
- The owner adds rules one at a time. Do not invent, reword or drop a rule; do not treat an empty section as permission.

## Global Rules

### R-1 Projects are in URP
**Rule:** every project is a URP project. Check its materials first. If any material is missing, or is not a URP material, it must be fixed before anything else, and the user must be told about it.
**Applies to:** every project, new and existing.
**How to check:** list every material the project uses (assets, prefabs, scenes, particle and line renderers, UI graphics) and its shader; none may be null, missing, pink, Built-in (Standard, Legacy, Mobile) or otherwise not URP.

### R-2 Scene name: `Main` is recommended
**Rule:** a project's entry scene should be named `Main` and sit in a `Scene` or `Scenes` folder (`Scene(s)/Main`). If `Main` exists it is the recommended entry scene. Other scene names are accepted, so a project may have several scenes (for example one per exhibit).
**Applies to:** every project, new and existing.
**How to check:** the project's scenes are listed in its Game Info So and registered on the launcher; if one is named `Main` it is the entry scene. A project with no `Main` is not a violation, but note it in the hand-off.

### R-3 One UI/UX, animation and sound across the whole project
**Rule:** UI/UX, button animations, 3D models, the sound on a button click and the effect of hovering over a button must all match across the entire project. The reference is the `Assets/Games/kmax-human-anatomy` project: its UI/UX, colours, animations, text style, spacing, placement and arrangement, and everything relevant to them.
**Applies to:** every project, new and existing.
**How to check:** compare the project against the reference and against `docs/Design.md` (colours, fonts and sizes, button size, spacing, placement, hover and press animation, click and hover sounds, model look) and list every difference.

### R-4 Unusual differences are reported first
**Rule:** if anything is found that differs from these rules (or is otherwise unusual against them), tell the user about the difference, suggest the changes to make it first, and show a warning message. Do not carry on silently.
**Applies to:** every project, new and existing, and every change.
**How to check:** the hand-off lists each difference found, with a warning and a suggested change.

### R-5 Same home screen and same experience
**Rule:** the home screen design and how it works, in any newly added project, must be the same as in the `kmax-human-anatomy` project: a seamless, uniform experience.
**Applies to:** every newly added project (existing projects should be brought in line, and differences reported under R-4).
**How to check:** compare the project's home screen with the reference: layout, cards, preview, Load button, transitions, what happens when idle, how a visitor leaves a topic and comes back, and the Home button to the launcher.

### R-6 Same stylus and pointer interaction everywhere
**Rule:** how the stylus is used must be uniform across the launcher and every project: click, grab, drag to move, select, and every other interaction (the mouse equivalents too). The same gesture must do the same thing in every project, with the same feedback. The reference is the `Assets/Games/kmax-human-anatomy` project.
**Applies to:** every project, new and existing.
**How to check:** list each interaction the project offers (click, grab, drag to move, select, rotate, zoom, pan, release, press-and-hold) with its stylus button and mouse mapping, and compare it with the reference; note any gesture that is missing, different, or gives different feedback.

### R-7 Every home screen has a Home button to the launcher
**Rule:** the home screen of every scene a project offers must have a Home button, and it is mandatory. It loads the launcher scene (`KmaxLauncherScene`), so a visitor lands on the launcher's home screen. If a scene has no Home button, add one at the top left, built the same way as the Home button of `kmax-human-anatomy` (glass button, 150 x 42, 32 px from the left and 22 px from the top of the 1920 x 1080 canvas, label "Home").
**Applies to:** every project, new and existing.
**How to check:** open each scene the launcher can open; its home screen has a Home button at the top left that opens `KmaxLauncherScene`, and it hides itself only when the launcher is not in the build (the project running alone).

### R-8 Newly added projects: change the look, never the behaviour
**Rule:** in a newly added project, do not alter or change the behaviour or functionality of its buttons or interactions. Work only on visuals: UI/UX, button effects, animations and the like, so that every project looks and feels uniform. Anything that would change what a button or interaction does (including making stylus or pointer gestures uniform under R-6) is reported to the user first under R-4 and not done on my own. The only behaviour added is what a rule requires, namely the Home button of R-7.
**Applies to:** every newly added project; for existing projects, ask before changing behaviour.
**How to check:** compare the project's buttons and interactions before and after the change; what each one does is unchanged, and the diff touches only appearance (sprites, colours, fonts, sizes, positions, animation and sound parameters) plus the R-7 Home button.

### R-9 One generic loading screen for the whole application
**Rule:** there is exactly one loading screen, `KMaxLoadingScreen` (prefab `KMax-launcher-unity/Resources/KMaxLoadingScreen.prefab`, script `LoadingScreen`). It is a slate backdrop that fills the whole view and is drawn as a world-space canvas at the screen plane in front of the camera (once per eye on the stereo display, not a screen-space overlay), one Animated Loading Icons ring in accent bright `#22D3EE`, and the text "Loading...", faded in before a scene change and faded out after it. No project builds its own loading screen, spinner or fade; every scene change (launcher Load, Home buttons, scene-to-scene buttons) goes through `LoadingScreen.Load`. Projects reach it by reflection through their own small `SceneLoader` helper (no assembly reference to the launcher) and fall back to `SceneManager.LoadScene` when it is absent.
**Applies to:** every project, new and existing.
**How to check:** search the project for `SceneManager.LoadScene` / `LoadSceneAsync`: only the `SceneLoader` fallback and `LoadingScreen` itself may call them; in play mode a scene change shows the loading screen once and `FindObjectsByType<LoadingScreen>` returns one instance.

### R-10 Exhibit screen layout, navigation and backdrop motion
**Rule:** every exhibit screen follows `docs/Design.md` 6.1 and 6.2: title and one-line description top left, the controls column top right starting with Menu (Menu is the screen's way out, so no separate Back or Home button), Previous / Next as the anatomy text buttons above the caption card, control instructions and part information in the always-visible bottom-centre caption card, and backdrop particles that never rotate with the model or the orbiting view.
**Applies to:** every project, new and existing.
**How to check:** open each scene; the zones match Design.md 6.1 and 6.2; Menu works; in play mode orbit or rotate the model and the ambient particles stay still on screen.

### R-11 One stylus standard in every scene
**Rule:** every scene that shows a model or lets the visitor navigate uses the stylus standard of the Inline-Four Engine scene (`kmax-display-example/Scenes/VirtualExhibition WR`, script `AnatomyStylusInput`; the same values are in `kmax-human-anatomy` `StylusNavigation` and in `kmax-automobile-engine` `StylusViewControl`). The mouse does the same thing in each scene.

| Pen button | Gesture | What it does | Value |
|---|---|---|---|
| 0 (front) | tap | click, select, press an interface button | the input module's primary key |
| 0 | press on a part and drag | grab and move that part (scenes with movable parts) | event-system drag |
| 0 | press on empty space or a model, then turn the wrist | rotate the view (wrist turn) | gain 1.35, starts after 1.5 degrees |
| 1 | tap (0.6 s or less) | reset the view (no pen vibration, R-13) | same as the Reset button |
| 2 (centre) | hold and move the pen | zoom: pen towards the screen scales the model down (zoom out), pen away from the screen zooms in | 1.6 m per m of pen travel |

A press that starts on an interface button belongs to the button and never rotates the view. New projects either use `AnatomyStylusInput` with the Volvo-style rig (`ViewerFlyController`), or `StylusViewControl` when the scene turns its own model. Do not invent another mapping, gain or button.
**Applies to:** every project, new and existing (R-6 asks the same; this rule fixes the exact values).
**How to check:** in each scene, press and turn with button 0, tap button 1, hold button 2 and push or pull; the view must rotate, reset and zoom as above, and an interface press must not rotate it.

### R-12 One panel at a time in the bottom centre
**Rule:** the bottom centre of a screen shows one information panel at a time (`docs/Design.md` 6.1). While a part's information panel is shown, the idle caption card, hint and prompt are hidden; they come back when it closes. No interface element may overlap another: panels, buttons, counters, labels and text are laid out apart (Previous / Next and the counter sit above the card, never over it). The loading screen is drawn in the 3D scene at the screen plane, not as a flat overlay (R-9).
**Applies to:** every project, new and existing.
**How to check:** open the scene, select a part or step to the next one, and look at the bottom centre: no text or panel shows through or sits on another. In the exhibits `ExhibitBottomPanelGate` does this.

### R-13 The stylus never vibrates
**Rule:** haptic feedback of the stylus is off in the whole application, at all times: no pulse on hover, hit, grab, release, reset, click, snap or error, and none from sound cues. Code must not call `KmaxStylus.VibrationOnce`, `Vibrate` or any other pen vibration. `StylusHaptics.Pulse` (kept so existing calls still compile) sends nothing, and `StopVibration` stays so a pen is never left buzzing. New scripts, projects and copied pen scripts follow this too.
**Applies to:** every project, new and existing.
**How to check:** search the code for `VibrationOnce` and `.Vibrate(`: there must be no call outside the SDK; on the display, hover, click, grab and release with the pen and feel nothing.

### R-14 The ray ignores what cannot be used
**Rule:** the stylus ray only touches things the visitor can use. (a) On the launcher and every home screen the ray is limited to the interface (`StylusUiOnlyRay` on the canvas: the interface is put on the UI layer and the pen's mask is that layer), so the beam and tip never land on the turntable models or the backdrop. (b) While the pen holds an object (`StylusGrab`, the PCB distance grab, a Pontiac Assembly part) the pen's ray hits nothing, so the beam, tip and hover do not jump onto other objects; its own mask is put back on release.
**Applies to:** every project, new and existing.
**How to check:** on a home screen sweep the pen over a model: the tip does not land on it, only on buttons; hold an object and carry it past others: the beam keeps its length and nothing highlights; after release hover works again.

### R-15 Standard session strip and result card gating
**Rule:** every experience with a timed interactive session shows the standardized KMax Interaction Kit session strip (520x56 glass pill, timer countdown mm:ss, score counter, 3 star slots) anchored at top centre (`docs/Design.md` 6.3). When a session finishes, the result summary card (640 px glass panel, large stars, score, breakdown rows, Try Again, Next) is displayed in the bottom-centre exhibit zone, gating and hiding any idle caption card or prompt via `CanvasRenderer.cull` (R-12). All scoring thresholds and star awards must strictly follow `ScoreRules` (a finished session awards at least 1 star; 0 stars indicates incomplete or invalid configuration).
**Applies to:** every experience incorporating timed interactive sessions, challenges, or scored assembly tasks.
**How to check:** start an interactive session: the 520x56 strip appears at top centre and ticks down; let the session complete: the result card appears at bottom centre, all background caption cards and prompts vanish without visual doubling or overlap, and star count matches the computed ScoreRules criteria.
